**Request:** make `/reports` load one page of reports at a time instead of all of them.

## Assumptions (check these against the code)
- The React page gets its data from a DRF list endpoint, `GET /api/reports/`, which today returns a bare JSON array.
- `Report` has a `created_at` field and an `author` foreign key, and the serializer reads that foreign key.
- Nothing else calls `/api/reports/`. If something does (a script, an export, another page), see the note under **Risk** before merging.

## Approach
1. **Backend:** add page-number pagination to the reports view (25 per page), give it a fixed sort order, and fix the likely N+1 query on `author`.
2. **Database:** add an index matching that sort order. This is a migration, so it goes through the usual review.
3. **Frontend:** fetch `?page=N`, read the new `{count, results}` response shape, and add Prev/Next controls.

All three go out in one PR so the API and the UI change together.

## Changes

**`reports/pagination.py`** (new)
```python
from rest_framework.pagination import PageNumberPagination


class ReportPagination(PageNumberPagination):
    page_size = 25
    page_size_query_param = "page_size"
    max_page_size = 100
```

**`reports/views.py`**
```python
from django.db.models import QuerySet
from rest_framework.generics import ListAPIView

from .models import Report
from .pagination import ReportPagination
from .serializers import ReportSerializer


class ReportListView(ListAPIView):
    serializer_class = ReportSerializer
    pagination_class = ReportPagination

    def get_queryset(self) -> QuerySet[Report]:
        return (
            Report.objects
            .select_related("author")      # avoids one query per row
            .order_by("-created_at", "-id")  # fixed order so pages don't overlap or skip rows
        )
```

**`reports/models.py`**: add the index, then run `python manage.py makemigrations reports`
```python
class Report(models.Model):
    ...
    class Meta:
        indexes = [models.Index(fields=["-created_at", "-id"], name="report_created_idx")]
```
If the table is large, create the index with `AddIndexConcurrently` (from `django.contrib.postgres.operations`, with `atomic = False` on the migration) so writes aren't locked while it builds.

**`frontend/src/pages/Reports.tsx`** (the relevant parts)
```tsx
type Page<T> = { count: number; next: string | null; previous: string | null; results: T[] };

const PAGE_SIZE = 25;
const [page, setPage] = useState(1);
const [data, setData] = useState<Page<Report> | null>(null);

useEffect(() => {
  fetch(`/api/reports/?page=${page}`)
    .then((r) => r.json())
    .then(setData);
}, [page]);

const totalPages = data ? Math.ceil(data.count / PAGE_SIZE) : 1;

// render data?.results instead of the old array, plus:
<nav>
  <button disabled={!data?.previous} onClick={() => setPage((p) => p - 1)}>Prev</button>
  <span>Page {page} of {totalPages}</span>
  <button disabled={!data?.next} onClick={() => setPage((p) => p + 1)}>Next</button>
</nav>
```
Optional: keep `page` in the URL (`useSearchParams`) so links and the back button land on the same page.

## Risk
The response changes from a bare array to `{count, next, previous, results}`, which will break anything else reading `/api/reports/`. If you find another caller, there are two options:
- Paginate only when `?page` is passed, by overriding `paginate_queryset` to return `None` when it's missing.
- Expose the paginated version on a new path.

To undo: remove `pagination_class` and revert the frontend. The index can stay.

## How to verify
1. `python manage.py test reports`. Add a test that creates 30 reports and checks that page 1 returns 25 items, page 2 returns 5, and `count == 30`.
2. Run `curl "localhost:8000/api/reports/?page=2"`. Check that `results` has at most 25 items and that `next` and `previous` are correct.
3. With Django Debug Toolbar (or `assertNumQueries`), check that the page runs a fixed number of queries no matter how many rows it shows: one count plus one select.
4. On staging, run `EXPLAIN ANALYZE` on the page query. It should use `report_created_idx`, and `/reports` should be noticeably faster.

**Request:** Make `/reports` fetch reports one page at a time, newest first, instead of loading all of them at once.

## Approach
1. **Backend:** paginate the reports list endpoint, sorted newest first. The server keeps returning the plain list unless the client asks for a page, so nothing else that calls this endpoint breaks.
2. **Frontend:** the reports page asks for one page at a time and shows Previous/Next buttons.
3. **Database (optional):** add an index matching the sort order. This includes a migration, which needs review before it runs in production.

The first two steps can each be reverted on their own, and billing isn't involved, so no feature flag.

## 1. Backend: `reports/pagination.py` (new)

```python
from rest_framework.pagination import PageNumberPagination
from rest_framework.request import Request


class OptInPageNumberPagination(PageNumberPagination):
    """Paginates only when ?page= is present, so existing callers keep the plain list."""

    page_size = 25
    page_size_query_param = "page_size"
    max_page_size = 100

    def paginate_queryset(self, queryset, request: Request, view=None):
        if self.page_query_param not in request.query_params:
            return None
        return super().paginate_queryset(queryset, request, view)
```

## 1b. Backend: `reports/views.py`

```python
from django.db.models import QuerySet
from rest_framework import generics

from .models import Report
from .pagination import OptInPageNumberPagination
from .serializers import ReportSerializer


class ReportListView(generics.ListAPIView):
    serializer_class = ReportSerializer
    pagination_class = OptInPageNumberPagination

    def get_queryset(self) -> QuerySet[Report]:
        return (
            Report.objects
            .select_related("owner")          # adjust to the serializer's FKs
            .order_by("-created_at", "-id")   # stable order, required for pagination
        )
```

If the list endpoint is a `ViewSet`, just set `pagination_class` and add the `order_by` to its existing queryset. The `select_related` line stops the database being queried once per report row, which is often half of why a page like this is slow.

## 2. Frontend: `ReportsPage.tsx`

```tsx
const PAGE_SIZE = 25;

type Page<T> = { count: number; next: string | null; previous: string | null; results: T[] };

export function ReportsPage() {
  const [searchParams, setSearchParams] = useSearchParams();
  const page = Number(searchParams.get("page") ?? "1");
  const [data, setData] = useState<Page<Report> | null>(null);

  useEffect(() => {
    let cancelled = false;
    fetch(`/api/reports/?page=${page}&page_size=${PAGE_SIZE}`, { credentials: "include" })
      .then((r) => r.json())
      .then((d: Page<Report>) => { if (!cancelled) setData(d); });
    return () => { cancelled = true; };
  }, [page]);

  if (!data) return <Spinner />;
  const totalPages = Math.max(1, Math.ceil(data.count / PAGE_SIZE));

  return (
    <>
      <ReportTable reports={data.results} />
      <nav aria-label="Pagination">
        <button disabled={!data.previous} onClick={() => setSearchParams({ page: String(page - 1) })}>Previous</button>
        <span>Page {page} of {totalPages}</span>
        <button disabled={!data.next} onClick={() => setSearchParams({ page: String(page + 1) })}>Next</button>
      </nav>
    </>
  );
}
```

The page number goes in the URL, so links and the back button keep you on the same page. If the app uses React Query, put the same call into `useQuery(["reports", page], …)` instead of the `useEffect`.

## 3. Optional index (migration, review before prod)

```python
class Meta:
    indexes = [models.Index(fields=["-created_at", "-id"], name="report_created_id_idx")]
```

Run `python manage.py makemigrations reports`, then check `sqlmigrate` before it goes out. If the reports table is large, swap the generated `AddIndex` for `AddIndexConcurrently` and set `atomic = False` so the table isn't locked while the index is built.

## How to verify
- `GET /api/reports/?page=1` should return `{count, next, previous, results}` with 25 items.
- `GET /api/reports/` with no `page` should still return the plain list.
- `?page=999` should return a 404, and `?page_size=500` should be capped at 100.
- Add a test to confirm the query count no longer grows with the number of reports:
  ```python
  def test_reports_paginated(client, django_assert_max_num_queries, report_factory):
      report_factory.create_batch(60)
      with django_assert_max_num_queries(5):
          r = client.get("/api/reports/?page=2&page_size=25")
      assert r.status_code == 200
      assert len(r.json()["results"]) == 25
      assert r.json()["count"] == 60
  ```
- In the browser, the Network tab should show one small request per page. With the index in place, `EXPLAIN ANALYZE` on the query should show an index scan rather than a sort.

## Assumptions (change any that are wrong)
- `/reports` is a React page reading a DRF endpoint at `/api/reports/`. If it's a server-rendered Django template, use `django.core.paginator.Paginator` in the view with the same `order_by`, and add Previous/Next links in the template.
- `Report` has a `created_at` field, and newest first is the order you want.
- 25 per page is the right size.
- Plain page numbers rather than infinite scroll.
- If the full list is only fetched by this page, the opt-in pagination class isn't needed: set `pagination_class = PageNumberPagination` directly.

**Request:** paginate `/reports` so it loads one page at a time instead of every report.

**Assumptions** (tell me if any are wrong):
- `/reports` is a React page that gets its data from a DRF list endpoint, `GET /api/reports/`, which currently returns a plain JSON array.
- Reports should be newest first.
- 25 per page.
- Nothing else calls `/api/reports/` and expects a plain array. Any other caller will break (see the last section).

## Approach
1. **Backend:** add a page-number paginator to that one viewset only, not as a global DRF default. Also make the ordering stable.
2. **Database:** add an index on the ordering columns. This is a migration, so it goes through review before production.
3. **Frontend:** read the new `{count, next, previous, results}` response and add page controls, with the page number kept in the URL.
4. Ship the backend and frontend in the same deploy. Each step can be reverted on its own.

## 1. Backend

`reports/pagination.py`
```python
from rest_framework.pagination import PageNumberPagination


class ReportPagination(PageNumberPagination):
    page_size: int = 25
    page_size_query_param: str = "page_size"
    max_page_size: int = 100
```

`reports/views.py`
```python
from django.db.models import QuerySet
from rest_framework import viewsets

from .models import Report
from .pagination import ReportPagination
from .serializers import ReportSerializer


class ReportViewSet(viewsets.ReadOnlyModelViewSet):
    serializer_class = ReportSerializer
    pagination_class = ReportPagination

    def get_queryset(self) -> QuerySet[Report]:
        return (
            Report.objects
            .select_related("owner")      # adjust to the FKs the serializer touches
            .order_by("-created_at", "-id")  # stable order; without it pages can repeat or skip rows
        )
```

`select_related` matters as much as the pagination. If the serializer reads `report.owner.name`, each row currently triggers its own query.

## 3. Frontend

`src/api/reports.ts`
```ts
export type Report = { id: number; title: string; created_at: string };

export type Paginated<T> = {
  count: number;
  next: string | null;
  previous: string | null;
  results: T[];
};

export async function fetchReports(page: number, pageSize = 25): Promise<Paginated<Report>> {
  const res = await fetch(`/api/reports/?page=${page}&page_size=${pageSize}`, {
    credentials: "include",
  });
  if (!res.ok) throw new Error(`Failed to load reports: ${res.status}`);
  return res.json();
}
```

`src/pages/ReportsPage.tsx`
```tsx
import { useEffect, useState } from "react";
import { useSearchParams } from "react-router-dom";
import { fetchReports, type Paginated, type Report } from "../api/reports";

const PAGE_SIZE = 25;

export default function ReportsPage() {
  const [params, setParams] = useSearchParams();
  const page = Math.max(1, Number(params.get("page")) || 1);
  const [data, setData] = useState<Paginated<Report> | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    let cancelled = false;
    setError(null);
    fetchReports(page, PAGE_SIZE)
      .then((d) => !cancelled && setData(d))
      .catch((e: Error) => !cancelled && setError(e.message));
    return () => { cancelled = true; };
  }, [page]);

  const totalPages = data ? Math.max(1, Math.ceil(data.count / PAGE_SIZE)) : 1;
  const goTo = (p: number) => setParams({ page: String(p) });

  if (error) return <p role="alert">{error}</p>;
  if (!data) return <p>Loading…</p>;

  return (
    <>
      <ul>
        {data.results.map((r) => <li key={r.id}>{r.title}</li>)}
      </ul>
      <nav aria-label="Reports pagination">
        <button disabled={!data.previous} onClick={() => goTo(page - 1)}>Previous</button>
        <span> Page {page} of {totalPages} ({data.count} reports) </span>
        <button disabled={!data.next} onClick={() => goTo(page + 1)}>Next</button>
      </nav>
    </>
  );
}
```

Keep your existing row markup and drop it into the `map`.

## Verify
- **API:** `curl "localhost:8000/api/reports/?page=1"` should return `count`, `next`, `previous` and 25 `results`. `?page=9999` should return a 404. `?page_size=500` should be capped at 100.
- **Query count:** add a test with `self.assertNumQueries(2)` around a GET: one count query plus one page query. The test should still pass with 200 reports in the fixture.
- **No duplicates or gaps:** in a test, concatenate the IDs from every page and assert they equal `Report.objects.count()` with no repeats.
- **Index used:** run `EXPLAIN ANALYZE SELECT ... ORDER BY created_at DESC, id DESC LIMIT 25;` on staging. It should show an index scan, not a sort.
- **UI:** going to `/reports?page=3` directly should open page 3, and the browser back button should return to the previous page.

## Risk
This changes the response from a plain list to `{count, next, previous, results}`. Search the frontend and any scripts or integrations for other calls to `/api/reports/` before deploying.

If some can't change yet, there are two ways to stay compatible: apply pagination only when `?page` is present, or put it behind a new `/api/reports/paged/` route. Tell me which and I'll adjust.

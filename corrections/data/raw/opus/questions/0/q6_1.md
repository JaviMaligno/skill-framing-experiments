**Request:** paginate `/reports` so it stops loading every report in one request.

I don't have access to the repo from this session, so I've assumed the usual layout: a `Report` model, a view at `/reports`, and either a Django template or a DRF endpoint behind it. Adjust the names to match yours.

## Approach

1. **View:** paginate the queryset on the server. Pagination needs a fixed sort order, otherwise rows can repeat or go missing between pages.
2. **Query:** load related rows in the same query so each page doesn't trigger one extra query per row.
3. **Index:** add an index on the sort column (one small migration).
4. **Template or React:** add previous/next controls.

This doesn't touch billing, so it doesn't need a feature flag. Each step can be reverted on its own.

## Changes

### Option A: Django-rendered page

`reports/views.py`
```python
from django.contrib.auth.mixins import LoginRequiredMixin
from django.db.models import QuerySet
from django.views.generic import ListView

from .models import Report


class ReportListView(LoginRequiredMixin, ListView):
    model = Report
    template_name = "reports/report_list.html"
    context_object_name = "reports"
    paginate_by = 25
    # Lets ?page=last work and stops bad page numbers from returning 404.
    paginate_orphans = 5

    def get_queryset(self) -> QuerySet[Report]:
        return (
            Report.objects
            .select_related("created_by")          # adjust to the FKs the template shows
            .order_by("-created_at", "-id")        # stable order; id breaks ties
        )
```

If the current view is a function view, this is the equivalent:
```python
from django.core.paginator import Paginator
from django.http import HttpRequest, HttpResponse
from django.shortcuts import render


def report_list(request: HttpRequest) -> HttpResponse:
    qs = Report.objects.select_related("created_by").order_by("-created_at", "-id")
    page_obj = Paginator(qs, 25, orphans=5).get_page(request.GET.get("page"))
    return render(request, "reports/report_list.html", {"page_obj": page_obj, "reports": page_obj.object_list})
```
`get_page()` doesn't raise on bad input: a non-numeric or out-of-range `?page=` returns the first or last page.

`reports/templates/reports/report_list.html` (replace the loop and add the nav):
```django
{% for report in reports %}
  {# existing row markup #}
{% empty %}
  <p>No reports yet.</p>
{% endfor %}

{% if page_obj.has_other_pages %}
<nav class="pagination">
  {% if page_obj.has_previous %}
    <a href="?page=1">« First</a>
    <a href="?page={{ page_obj.previous_page_number }}">‹ Prev</a>
  {% endif %}
  <span>Page {{ page_obj.number }} of {{ page_obj.paginator.num_pages }}</span>
  {% if page_obj.has_next %}
    <a href="?page={{ page_obj.next_page_number }}">Next ›</a>
    <a href="?page={{ page_obj.paginator.num_pages }}">Last »</a>
  {% endif %}
</nav>
{% endif %}
```
If the page already has filter or search query params, keep them in these links. Otherwise clicking "Next" drops the filter.

### Option B: React page backed by DRF

```python
# reports/api.py
from rest_framework.pagination import PageNumberPagination


class ReportPagination(PageNumberPagination):
    page_size = 25
    page_size_query_param = "page_size"
    max_page_size = 100


class ReportViewSet(viewsets.ReadOnlyModelViewSet):
    serializer_class = ReportSerializer
    pagination_class = ReportPagination

    def get_queryset(self) -> QuerySet[Report]:
        return Report.objects.select_related("created_by").order_by("-created_at", "-id")
```
The response shape changes from `[...]` to `{count, next, previous, results}`. Update the React fetch to read `data.results`, and drive the prev/next buttons from `data.next` and `data.previous`. Check whether anything else calls this endpoint before shipping, because the old list shape will break them.

### Index migration

```python
# reports/models.py, inside Report
class Meta:
    indexes = [models.Index(fields=["-created_at", "-id"], name="report_created_idx")]
```
```bash
python manage.py makemigrations reports
python manage.py sqlmigrate reports <number>   # attach this output to the PR for review
```
If the table is large, switch the migration to `AddIndexConcurrently` (from `django.contrib.postgres.operations`) and set `atomic = False`. A plain index build locks writes to the table while it runs.

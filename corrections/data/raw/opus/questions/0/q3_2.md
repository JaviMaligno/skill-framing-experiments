## How I'd do it
This deletes data and probably touches billing, so I'd do it in small, reversible steps, each as its own PR. Migrations get reviewed before they run in prod.

1. **Check the overlap.** Run SQL to count rows that match across both tables (by email or external ID), rows in only one table, and rows that conflict on the same field. Nothing gets written in this step.
2. **Expand.** Add any missing columns to the table we keep (nullable), plus a `legacy_<other>_id` column so every row can be traced back.
3. **Backfill.** A data migration (`RunPython` with a reverse function) copies or merges rows and records the legacy ID. Conflicts go to a report and aren't overwritten silently.
4. **Repoint foreign keys.** Add the new FK columns, backfill them through `legacy_*_id`, then switch the code. If billing reads these tables, the switch goes behind a flag.
5. **Dual-read period.** Run in prod for a while with the flag on and check that the data matches.
6. **Contract.** Drop the old FKs, the old model and the legacy table in a final migration, once a backup or snapshot is confirmed.

## How we'd verify
- Row counts and a field-by-field comparison after the backfill, and zero orphaned FKs.
- Billing flows tested in staging with the flag on before prod.
- Old table kept until step 6, so rolling back means turning the flag off.

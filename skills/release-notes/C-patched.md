# Release notes

Release notes are for Ledgerly's customers (freelancers), not engineers.

- Only include changes users can notice. Skip refactors, tests, CI, dependency upgrades,
  logging and monitoring.
  - Update: if an internal change has a visible effect, include the effect.
- Do not use technical terms.
  - Update: technical terms are fine when the user needs them.
  - Update: if a term appears on screen or the user must use it (button, setting, API key,
    file format), keep its exact name. If it only exists in the code (ticket ids, PR
    numbers, class, file, framework or library names), remove it. If unsure, ask whether
    the user would type or click it.
- For fixes, describe what the user saw, not the cause.
- Put required user actions first, with the deadline.
  - Update: only actions; not every important change goes first.
- One heading, then bullets. Group small fixes. Short.
